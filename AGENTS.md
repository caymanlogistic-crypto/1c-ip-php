# Одна задача — один агент — проверяемая сдача

## Один репозиторий, локальные worktree, один общий сайт

Репозиторий: `caymanlogistic-crypto/1c-ip-php`. `main` содержит принятые изменения. На сервере используется один общий экземпляр приложения; автодеплой разрешён только из `main`. Ветки задач и pull request не обновляют сайт. Не создавай серверные стенды для агентов. Существующий экземпляр UI используется как общий сайт без переноса его БД и документов; внутреннее имя `ui` не означает отдельный стенд для UI-задач.

Каждый агент начинает от актуального `origin/main` в отдельной локальной рабочей папке `git worktree` и своей ветке `task/...` или `codex/...`. Не пиши в чужой checkout. Локальная работа агентов может идти параллельно; постоянный координатор и автоматическое порождение субагентов не нужны.

До принятия проверяй задачу локально и показывай пользователю зафиксированный кандидат: commit, URL/роль, сценарий и остаток. Для параллельных запусков выделяй разные порты, имена cookie и каталоги сессий, изменяемые тестовые БД/данные, файлы и артефакты. Ветки и разные порты сами по себе не разделяют данные и cookie. Конфигурация и секреты worktree остаются вне Git. Порядок подготовки и запуска — START-HERE.md.

Команда пользователя «выкладывай» разрешает этому же агенту проверить и зафиксировать кандидата, опубликовать PR и поставить его в автоматическую очередь командой `./Queue-PR.ps1 -PullRequest <номер>`. Не выполняй прямой `gh pr merge`, merge через API/UI или push в main. Очередь сама обновляет ветку от main, проверяет точный commit, сливает и дожидается проверенной выкладки. Не требуй повторного разрешения на эти шаги. Если разрешение на публикацию не было дано, PR не ставится в очередь.

Слиянием и публикацией управляет `.github/workflows/merge-queue.yml`, один worker на репозиторий. Агентам не нужно вручную ждать друг друга или опрашивать чужие workflow. Заявка связана с точным одобренным head и хранится в PR; после постановки не меняй этот head. Статусы: queue:ready, queue:running, queue:blocked, queue:done. При конфликте/новом коде агент исправляет и проверяет кандидата, затем ставит новый head в очередь по действующему разрешению. При сбое уже слитой выкладки следующие слияния остановлены до исправления. Бесплатный GitHub этого приватного репозитория не поддерживает защиту main: прямой обход владельцем технически возможен, но агентам запрещён; очередь обнаруживает изменение main вне своего процесса и останавливается. Не отменяй чужую выкладку и не делай force-push. Локальная работа в своих worktree продолжается; отдельного сервера, БД очереди и постоянного агента-координатора нет.

Не правь рабочий код в контейнере: исходники → GitHub/main → workflow → образ → общий сайт. Данные, сессии и документы находятся вне образа. Обычный деплой не импортирует SQL и не применяет миграции. Откат образа не откатывает БД и внешние эффекты; несовместимая миграция требует отдельного плана.

Внешний admission, workers/outbox и профили отправок не включаются из-за смены схемы работы. Унаследованные очереди не проигрывай. Чтение одного провайдера — отдельная задача; внешняя отправка/запись — конкретное поручение с объектом/адресатом. WorkflowMaxEvent/RentalOutbox guards сохраняй. Витрина и приложение находятся в том же репозитории и публикуются вместе.

## Назначение

Развивать существующую PHP/MySQL-систему короткими завершёнными задачами. Каждый агент сам изучает нужный участок, делает изменение, проверяет, показывает владельцу и после принятия сам сохраняет результат. Постоянный координатор, цепочка проверяющих и автоматическое порождение субагентов не используются.

## Начало задачи и продолжение в новом чате

Прочитай START-HERE.md, текущую запись WORK.md и нужный раздел ARCHITECTURE.md. Для бизнес-правил используй CURRENT-SPEC.md. Затем открой фактический маршрут и код нужной функции. Не перечитывай всю историю, архивы и все модули перед небольшой правкой.

Установи каталог, Git status, текущую ветку, версию и окружение. Сохрани чужие изменения. При отсутствии информации отметь неизвестное; не считай старый отчёт фактом текущего запуска.

Выполняй только выданную задачу. Пользовательское поручение разрешает необходимые обратимые локальные действия в его пределах. Не спрашивай общее разрешение повторно. Явное поручение проверить подключение разрешает соответствующую проверку чтения, но не произвольные отправки или внешнюю запись.

## Владение изменениями

Один агент пишет в один принадлежащий ему worktree. Не меняй чужие файлы, процессы, БД или конфигурацию. Если выявлена общая изменяемая среда, останови только затронутую операцию и кратко назови конфликт пользователю; независимая локальная работа продолжается.

Worktree — обычный способ изоляции задачи, а не новое окружение на сервере. Не создавай отдельный клон репозитория, БД управления задачами, scheduler или тестовую платформу для обычной правки. Для бизнес-проверок используй отдельную разрешённую копию тестовых данных; общую серверную БД локальным агентам не подключай.

## Обязательное соответствие витрине

Перед UI-правкой открой Витрину и используй существующие компоненты. Изменение общего компонента и его примера в Витрине выполняется в одной ветке и задаче. Результат принимает пользователь; команда «выкладывай» разрешает публикацию текущей задачи. Адрес витрины — `/design/demo/index.html`, общие ресурсы — `public/design/system/` и `public/assets/source-*.js`. Фактическую доступность текущей версии проверь по START-HERE.md.

Перед любой видимой UI-правкой открой актуальную принятую витрину, указанную в ARCHITECTURE.md. Сверь тип компонента, геометрию, палитру, шрифт, состояния и поведение. Используй существующие общие компоненты.

Приложение и витрина используют одни источники CSS/JS/токенов и общие renderers там, где они есть. Не создавай вторую копию дизайн-системы или локальные переопределения ради похожего вида.

Новый/изменённый компонент и соответствующий пример витрины входят в одну задачу и одну сдачу. Если меняется только композиция формы из прежних компонентов, сверяй её с витриной; не обновляй витрину бессодержательно. Существующий утверждённый компонент не требует нового общего согласования. Новый визуальный вариант показывается владельцу в составе задачи.

Если витрина отсутствует или её актуальность не подтверждена, сообщи конкретный факт. Не объявляй старый CSS, скриншот или source-ui снимок действующим эталоном. Независимая backend-задача может продолжаться. Для принятия UI нужна доступная актуальная витрина.

## Архитектура

Сначала проследи URL → действующий handler → команду/сервис → данные → внешний эффект. В module.php есть переопределения маршрутов; имя Controller не гарантирует, что экран обслуживается им.

Сохраняй общий путь Service::command для основных команд аренды: права, версия, command_key, транзакция, история и событие. Не добавляй запись тех же данных из HTML-шаблона или нового обходного endpoint.

Для ручных писем из других страниц используй общий `Messaging::dispatchManualEmail`, а не новый SMTP-клиент или прямой транспорт. Права, actor/POST/CSRF, стабильный request_key, результаты по получателям и границы ручной/документной доставки описаны в [контракте почтового сервиса](ARCHITECTURE.md#общий-почтовый-сервис-для-других-страниц). Собственные права страницы/документа проверяет её handler; служебные guards и typed intent/RentalOutbox сохраняй.

Новое бизнес-правило размещай в одном авторитетном месте. Реестр, карточка и счётчики должны пользоваться одной семантикой. Разделяй живое состояние, исторический источник и вычисляемую проекцию; source_json/fact_json сейчас смешивают эти роли, поэтому перед изменением проверь конкретное поле.

При касании большого файла допустимо извлечь только нужную ответственность с сохранением поведения. Массовое переименование, новая платформа и перенос всех классов не являются частью узкой задачи.

Для MAX из других страниц используй [общий контракт модуля](ARCHITECTURE.md#max-module): существующий POST-handler или разрешённый локальный bridge для ручной команды, а для аренды — прежний путь события после commit. Не вызывай транспорт напрямую; сохрани права, actor из сессии, UUID групп, стабильный request_key и receipts. Новый экран не расширяет локальный/серверный допуск и не включает AutoMAX.

## Данные и подключения

Не удаляй бизнес-данные, неизвестные записи, watermark-строки, историю команд, попытки отправки или pending ради прохождения проверки. Не пересоздавай схему. Миграции и преобразования данных выполняй отдельной задачей на разрешённой копии с понятным возвратом.

Сохраняй денежную точность, финансовые инварианты, version/idempotency, права, занятость и доказательства документов. Не снимай бизнес-защиту для ускорения демонстрации.

Для подключения различай конфигурацию, вход, чтение, получение файла, локальный импорт и внешний эффект. Один живой исполнитель на конкретный провайдер/аккаунт. Не проигрывай outbox в новой копии. Не повторяй внешнюю операцию с неизвестным исходом до сверки её результата.

В archive есть разовые guards конкретных БД/версий; выясняй назначение точечного guard, не удаляй их массово. Значения ключей, credentials, cookies и приватные payload не попадают в Git, отчёты или скриншоты.

## Проверка

Минимум: diff, php -l изменённых PHP-файлов и один реальный сценарий затронутого поведения. JS проверяй средствами текущего проекта. UI проверяй в браузере рядом с витриной, включая короткое окно и нижние действия.

Для прав добавь разрешённый и запрещённый случай; для денег/занятости — затронутый инвариант; для повторных операций — отсутствие дубля. Используй имеющиеся адресные тесты. Если нужного теста нет, добавь небольшой тест конкретного риска. Полная регрессия нужна при изменении общего контракта или явном поручении, а не после каждой надписи.

Непроведённую проверку так и называй. Чтение исходника, HTTP 200 и число тестов не заменяют наблюдаемый результат. После двух одинаковых ошибок без новых данных прекрати повторы и сообщи конкретный блокер.

## Сдача и принятие

Перед сдачей зафиксируй кандидата и сообщи: задачу, результат, URL/роль, шаги проверки, commit, существенный остаток. Для UI укажи также URL/раздел витрины.

Пока пользователь проверяет, не меняй показанный кандидат без его нового поручения. После «выкладывай» этот же агент ставит зафиксированный PR в очередь и даёт ссылку на его статус. Не объявляй «опубликовано», пока ticket не стал done и версия/нужный сценарий не проверены. Ожидание очереди не блокирует другие локальные задачи в отдельных worktree.

Слияния выполняет очередь, сохраняя чужую работу. Конфликт автоматического обновления возвращается агенту без слияния. Если его разрешение заметно изменило поведение проверенного кандидата, адресно перепроверь и покажи изменившийся результат владельцу. Не переноси принятие на другой код молча. Отчётный commit после приёмки не должен менять прикладной код; укажи проверенный и итоговый commit при их различии.

Git-откат не откатывает БД, документы или внешние эффекты. Не восстанавливай старую БД поверх новых данных без отдельного основания. Публикацию текущей задачи разрешает «выкладывай». Это не разрешение на несвязанные изменения или перенос на другой сервер.

При завершении обнови только изменившиеся факты: WORK.md; START-HERE.md при смене среды; ARCHITECTURE.md при изменении точки входа/контракта/витрины; CURRENT-SPEC.md при согласованном изменении бизнес-правила.
