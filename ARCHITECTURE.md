## Среда и публикация

Текущий процесс — AGENTS.md и START-HERE.md: отдельный локальный worktree/ветка каждого агента, свои порты/сессии/изменяемые данные, один общий серверный экземпляр, последовательный GitHub merge и автодеплой main по «выкладывай». Существующие технические имена ui/ipphp-ui сохраняются; переход с прежних двух стендов выполнен 17.11.2026 и проверен, результат отражён в WORK.md. Receiver deploy/server/deploy.py допускает main OIDC; локальная сессия cli-server задаётся Start-Local.ps1 отдельно от серверных cookies. Бизнес-команды и внешние guards сменой процесса не меняются.

Доставка: `.github/workflows/staging.yml` сохраняет registry build cache и публикует main в приватный GHCR; `deploy/server/deploy.py` получает immutable digest через OIDC/SSH, загружает недостающие слои, проверяет image_id/commit и пересоздаёт только app. SOURCE_COMMIT после runtime/vendor сохраняет кеш между правками. SQL/миграций и переноса документов в этом пути нет; прежний image_id остаётся локально для отката. Порядок внедрения — deploy/README.md, проверенный статус — WORK.md.

Автоматическая очередь: `Queue-PR.ps1` → `merge-queue.yml` → `deploy/merge_queue.py`. Ticket head/статус хранятся в PR, один Actions worker проводит update/check/merge/deploy и проверяет квитанцию фактической версии. `staging.yml` принимает точный workflow_dispatch на ветку кандидата (build) или main (deploy); OIDC receiver разрешает только push/dispatch main. Внешних БД/процессов очереди нет. Бесплатный GitHub не даёт защитить main; инструкции запрещают агентам обход, controller обнаруживает постороннее изменение main.

## 3. Изменение бизнеса

Основной вход команд аренды: Service::command.

Он проверяет policy/права/роль, command_key, fingerprint повторной команды, версии изменяемых сущностей; выполняет бизнес-действие и запись результата/события в транзакции. Проверка версии находится в Service::version. Финансовые действия уходят через ExtraService в FinanceService; дополнительные сценарии имеют свои сервисы, но не должны обходить общий допуск.

Сеть и внешние эффекты не должны выполняться до подтверждённого сохранения бизнес-команды. В текущем коде часть уведомлений вынесена после commit; для отправок существуют отдельные intent/outbox/attempt механизмы. Улучшай этот путь по конкретной задаче.

| Факт | Основные данные | Где искать правило/запись | Особенность |
|---|---|---|---|
| Контрагент | parties, party_bank_accounts | PartyDirectory, Service | Блокировка влияет на ограниченный набор проектов |
| Договор | contracts, contract_objects, contract_terms | Service, ExtraService, ContractForm | Исторический и обслуживаемый договор различаются |
| ДС | rental_documents, document_terms | Addenda, AddendumController, ExtraService | Собственный цикл согласования и применения |
| Счёт | invoices, версии/базы выставления | FinanceService, InitialBilling, MonthlyBilling, InvoiceCalculation | Сумма и база выставления не меняются произвольно задним числом |
| Деньги | payments, payment_allocations | Service, FinanceService | Оплата и распределение — отдельные факты |
| Занятость | rental_objects, contract_objects, holds, reservations | Occupancy, ContractOccupancy, Availability | Исключённый объект может удерживаться до акта возврата |
| История/повторы | rental_commands, rental_events, audit | Service, WorkflowEvents, Audit | Не очищать ради повторной попытки |
| Внешний обмен | integration_connections, integration_runs, external_documents/files | ProviderService, Config, адаптеры | Логин, чтение, импорт и внешняя запись — разные результаты |

source_json и fact_json сейчас содержат смешанные исторические и изменяемые сведения. Их названия не определяют авторитетность. Для поля, которое меняет задача, явно установи: кто пишет, кто читает, что первично, что вычисляется. Не нормализуй все JSON без отдельной задачи.

Обнаружено расхождение: RegistryState::managed учитывает imported/workflowTouched/servicing_document_id; SourceCards::show учитывает только imported. Оно не считается исправленным этим документом.

### Правило развития

Рабочий компонент и его пример используют общую реализацию. Изменение компонента сопровождается обновлением примера в той же задаче. Витрина не хранит отдельную копию CSS/JS, которая может устареть.

Перед сдачей сравни пример и рабочий экран: размеры/отступы, палитра/типографика, normal/disabled/error состояния, фокус, прокрутка и нижние действия модального окна. Для общего компонента проверь один соседний экран. Смысл цветов задаётся CURRENT-SPEC, а не личным вкусом агента.

Новый компонент или новый визуальный вариант показывается владельцу. Применение существующего принятого компонента не требует отдельного разрешения на каждую кнопку.

### Общий почтовый сервис для других страниц

Email — общий backend-сервис, а `/email` — одна из его форм. Другая PHP-страница может отправить ручное письмо через `Modules\Integrations\Messaging::dispatchManualEmail`, используя тот же SMTP-профиль, журнал, вложения и защиту от дублей. Подключение страницы требует её собственного handler; наличие сервиса само по себе не добавляет кнопок или отправок.

**Вход для ручной отправки:**

```php
use App\{Auth, DB};
use Modules\Integrations\{Config, Messaging, Support};

$user = Auth::user() ?? throw new RuntimeException('Требуется вход', 401);
// Ключ создаётся один раз при показе формы через Support::uuid(), затем передаётся hidden-полем.
$requestKey = (string) ($_POST['request_key'] ?? '');
$attempts = (new Messaging(DB::pdo(), Config::store()))->dispatchManualEmail(
    actor: (int) $user['id'],
    requestKey: $requestKey,
    targets: $recipients,   // Массив адресов, явно указанных пользователем.
    text: $body,
    subject: $subject,
    attachments: $attachments // [] либо [['name' => 'file.pdf', 'bytes' => $bytes]].
);
```

Правила подключения:

1. Handler проверяет доступ к своей странице и бизнес-объекту. Общий метод дополнительно требует реальный POST, действующую сессию того же actor, `messaging.send`, уровень **2** страницы `connections.email` и валидный CSRF. Права новой страницы сами по себе не заменяют доступ к Email. Текущую сессию/POST/CSRF нельзя имитировать в фоновой задаче.
2. Получатели и содержание должны соответствовать явному действию пользователя. Для этой ручной команды разрешены адреса из формы без предварительного внесения в private `approved_recipients`; разрешение действует только в памяти текущего вызова. Приватный список не расширяется. `dispatch` для служебных отправок и RentalOutbox сохраняют собственные ограничения.
3. Использовать существующий `request_key` формы: 16–100 символов `[A-Za-z0-9-]`. Один ключ + то же содержание возвращает прежние попытки без повторного письма; изменение содержания с тем же ключом даёт конфликт. Не генерировать новый ключ внутри POST-handler ради повтора. Старый failed не отправляется заново тем же ключом; после сверки новая ручная попытка начинается со свежей формы. Pending/uncertain сначала сверяются, автоматического повтора нет.
4. Лимиты проверяет сервис: до 20 получателей, текст до 4000 и тема до 200 символов, до 10 файлов суммарно до 10 МиБ. Передавать массив адресов, а не строку CSV. Вложения — имя и байты; MIME/hash формирует общий сервис. Чтение файла из бизнес-документа и проверка права на этот файл остаются обязанностью вызывающего handler.
5. Возвращается массив попыток **по получателям**, с id/status/result_code. Показывать результаты каждого получателя и использовать общий `Controller::status` / `Controller::resultCode` для подписей. `accepted / SMTP_ACCEPTED_NOT_INBOX` означает приём SMTP-сервером, а не получение адресатом. Журнал `/email?tab=history`, claims и подписанные spool/receipt общие для всех вызывающих страниц.
6. Не создавать второй SMTP-клиент, отдельные пароли/настройки на каждой странице или прямые вызовы `mail()`/`MessageTransport` из шаблонов. Рабочий handler использует обычный `Messaging` без тестовой подмены транспорта. Настройки берутся через Config; серверный EmailAdmission и TLS-проверка сохраняются. Не включать общий внешний gate ради новой страницы.
7. Метод предназначен для явной ручной отправки. Он не разрешает рассылку при GET, открытии карточки, polling или фоновых событиях. Доставка утверждённых договоров/ДС/счетов использует существующий бизнес-командный путь и typed intent/RentalOutbox; простое письмо не меняет их статус доставки, согласование или доказательства. Отправлять нужно после commit бизнес-команды, без обхода её прав, версии и фиксации документов.

Проверка новой страницы: разрешённая роль и запрещённая роль, CSRF, новый адресат, повтор того же ключа без дубля и результаты по получателям. Сетевые тестовые письма отправляются только по конкретному поручению с адресатом; иначе использовать fixture-транспорт в изолированном тесте. Образец проверки контракта — `tests/manual-email.php`; тест низкоуровневого допуска — `bin/test-email-access.php`. Это не поручение подключить или включить автоматическую отправку на остальных страницах.

### Ограничения подключений

Ручная отправка `/email` → `Controller::action` → `Messaging::dispatchManualEmail` → `Messaging::dispatch` → `MessageTransport` допускает локальный `IPPHP_ALLOW_EMAIL=owner-authorized-email-access` или серверный EmailAdmission (`.local/email-admission.json`, только smtp.spaceweb.ru:465/TLS) при сохранении прав, CSRF, revision, spool/receipt и request_key. dispatchManualEmail проверяет POST, текущего пользователя, messaging.send и уровень страницы; адресат из формы разрешается только внутри текущей команды, без изменения private approved_recipients. Служебный dispatch и RentalOutbox сохраняют прежние ограничения получателей. Локальный Start-Local получает этот допуск только из собственного boolean `email_enabled`; preflight сверяет их. Общий gate и guards RentalOutbox/WorkflowMaxEvent этим параметром не включаются. SMTP SSL/TLS и STARTTLS проверяют сертификат; учётные данные и allowlist остаются вне Git.

1. В ZIP среди private/integrations есть только key и max.enc. Остальные профили и .local не переданы; их фактическое наличие проверяется локально.
2. WorkflowMaxEvent::dispatch привязан к старой R2-БД и порту. AutoMAX из CURRENT не является работающим. Общая проверка MAX и специальный MaxReadCheck — разные пути.
   Локальный worktree может явно включить `LocalMaxReadCheck` через `bin/max-local-read-setup.php --enable`. Маршрут `/integrations/action`, provider=max/action=check использует этот путь только при наличии приватного `.local/max-read-access.json`. Доступ ограничен Windows CLI/cli-server, собственной `ipphp_task_*` БД/пользователем на 43061, сверенной копией, revision и hash vault, активными группами и правами пользователя. Разрешены только последовательные GET `/me` и `/chats/{chat_id}/members/me`, под общей блокировкой провайдера, с существующими claims/receipts/idempotency. Общий внешний допуск и WorkflowMaxEvent/RentalOutbox не включаются. Отдельное разрешение владельца и `--enable-manual-send` добавляют в приватный marker единственный разрешённый chat_id группы «ТЕСТОВАЯ»: `dispatchManual` допускает один POST `/messages?chat_id=...` с неизменным JSON тела конкретной команды, через обычный Messaging claim/receipt/idempotency. Другие адресаты, пути, методы и повтор HTTP в одной команде отвергаются. MaxSettings распознаёт сохранение прежних полей и сохраняет revision/привязку; ошибки spool/secret до входа в транспорт дают failed вместо ложного uncertain. На Linux этот локальный допуск отвергается.
3. Отсутствие .local/onec-dev-transport.json выбирает direct. Не меняй транспорт молча при переносе.
4. GET_LOCK использует ipphp-provider:{provider} на уровне MySQL-сервера; разные схемы могут конкурировать за один провайдер.
5. Наличие другой pending-операции блокирует новые действия провайдера. Сначала выясняй прежний исход.
6. Банк может иметь результат общей авторизации с network_calls=0; это не доказательство чтения выписки.
7. RentalOutbox связывает политику с project/release/digest/получателями. Копия и новый commit не получают автоматически прежнее право отправки.
8. При неизвестном исходе внешнего действия выполняется сверка прежней операции. Новая попытка не должна создавать дубль.

### MAX: общий модуль для других страниц

Смена активности объектов (поручение 18.11): `object.save` остаётся в `Service::command`/`ExtraService`; дата `active_on` записывается в существующие периоды. `ObjectActivity` связывает реальный переход с существующими rental_events/rental_commands, actor/auth_version, версией объекта, датой и checksum. Наружу Service выдаёт ID только своего свежего committed события; повтор/rollback не выдают его. Controller вызывает `ObjectActivityMax` после commit. Этот узкий потребитель проверяет POST, текущую роль M/admin, rental.read/write, уровень objects, receipt команды и текущую версию/состояние; текст берётся из события, адресат — единственная активная группа «ТЕСТОВАЯ», ключ доставки стабилен по событию/команде.

В разрешённом Windows worktree он использует `LocalMaxReadCheck::dispatchObjectActivity` → общий `Messaging`/`MessageTransport`/HMAC receipt. Отдельная доменная capability подтверждённого события не выдаёт менеджеру права ручной рассылки: прежний `dispatchManual` продолжает требовать messaging.read/send и connections.max. Приватные root/DB/revision/vault/approved chat guards и provider lock сохраняются; перед транспортом событие проверяется заново. Вне такого допуска применяется только уже разрешённый общий транспорт; при выключенном external gate возвращается `unavailable`, а реестр показывает правдивый результат. Windows-допуск не работает на Linux и на общий сайт не переносится автоматически. `WorkflowMaxEvent`/`RentalOutbox` и прежние каталоги событий не менялись, очереди не сканируются и не повторяются. Проверки — `tests/object-activity.php`, прежние local-max tests и адресная живая проверка двух переходов.

Модуль MAX можно использовать из других страниц этого PHP-приложения. Страница `/max` — один из его потребителей, а не отдельная реализация отправки. Новый экран использует существующие команды, настройки, группы и историю; собственный HTTP-клиент MAX, хранилище токенов и обходной endpoint не создаются. Доступность отправки проверяется в конкретной среде: наличие классов в образе её не включает.

| Задача страницы | Общий путь | Условия и результат |
|---|---|---|
| Проверить подключение | POST `/integrations/action`, `provider=max`, `action=check` | Текущие сессия, CSRF, права и `request_key`; выбранный допуск проверяет токен и членство бота. Сообщения не отправляются. |
| Явно отправить текст пользователем | Тот же POST, `action=send`, `targets[]`, `text` | `targets[]` содержит локальные UUID `messaging_groups.id`, а не произвольные внешние `chat_id`. Существующий локальный допуск разрешает одну группу «ТЕСТОВАЯ». |
| Вызвать локальную команду из серверного кода | `$max = new LocalMaxReadCheck($db)`; затем `$max->dispatch($actorId, $requestKey)` / `$max->dispatchManual($actorId, $requestKey, [$groupId], $text)` | Только подготовленный Windows worktree и разрешённая область; вызов вне бизнес-транзакции. Это не универсальный серверный допуск. |
| Уведомить о бизнес-событии аренды | `Service::command` → свежий committed event → `WorkflowMaxEvent::afterCommittedCommand` | Существующий rental Controller вызывает этот путь после commit, до ответа пользователю. Требуются допуск среды, разрешённое событие, группа и версия шаблона. |

Источники: [маршруты](modules/integrations/module.php), [handler формы](modules/integrations/Controller.php), [Messaging](modules/integrations/Messaging.php), [локальный допуск](modules/integrations/LocalMaxReadCheck.php), [бизнес-события MAX](modules/integrations/WorkflowMaxEvent.php). Низкоуровневый `Messaging::dispatch` сам по себе не заменяет проверку пользователя/прав, а `MessageTransport` не является публичным API для страницы.

Правила подключения нового экрана:

1. **Ручная команда — только по явному действию пользователя.** Использовать POST и штатный CSRF. Actor брать из текущей серверной сессии, не из полей формы. Для ручного локального пути обязательны `messaging.read`, `messaging.send` и уровень редактирования `connections.max`; право на исходную страницу не даёт право отправлять в MAX. Общий handler дополнительно применяет `PagePolicy` к провайдеру. Штатный ответ формы переводит в `/connections/max` к результату/журналу; произвольного `return_url` текущий контракт не поддерживает.
2. **Одна команда — один стабильный `request_key`.** Для повторного запроса той же операции сохранять прежний ключ и payload: `Messaging` возвращает существующую попытку без новой отправки. Новый ключ означает новую операцию и не служит обходом pending/uncertain. Сначала сверить прежний результат, не удалять историю и не запускать автоматический повтор.
3. **Одна общая цепочка доставки.** Допуск → `Messaging` → зафиксированный claim/spool → `MessageTransport` → HMAC receipt и публичный результат. Внешний вызов выполняется после commit claim. Прямой cURL из HTML, JavaScript или нового handler обходит эту цепочку и недопустим. GET, рендеринг страницы, обновление счётчиков и открытие карточки не отправляют сообщения.
4. **Получатели и профиль общие.** Группа разрешается через `messaging_groups` и приватный approved list/marker; токен читается через `Config`, не передаётся в браузер, Git или журнал. Для текущего MAX — непустой текст до 4000 символов, без темы и вложений. HTTP body формирует транспорт. Смена revision, vault или набора групп закрывает прежний локальный допуск; сохранение неизменённых настроек оставляет revision прежней (`MaxSettings`). Новый экран не включает общий external gate, workers, AutoMAX или `RentalOutbox`.
5. **Бизнес-уведомление — из события, не из шаблона страницы.** Сохранить путь `Service::command`, его права, версию, `command_key`, транзакцию и историю. Существующий hook получает только свежий event ID после успешного commit; черновик, rollback и повтор команды нового уведомления не создают. Текст/версию бизнес-шаблона брать через `TemplateCatalog` по событию. Новый вид события добавляется согласованно в `WorkflowEvents::transition`, `WorkflowMaxEvent::select`, каталог и явно разрешённую область; наличие шаблона само по себе запуском не является. Не дублировать существующий hook на другой странице.
6. **Локальный допуск не переносится между средами.** `LocalMaxReadCheck` связан с Windows CLI/cli-server, собственными root/БД/пользователем, проверенной копией, revision, vault и группами. На Linux он отказывает. Исторический `WorkflowMaxEvent` имеет отдельные guards старой R2-БД/версии и postcommit-режима; новый потребитель их не ослабляет. Работающая локальная кнопка не доказывает включённую отправку на общем сайте. Подготовка локального допуска — [START-HERE.md](START-HERE.md#локальная-проверка-подключения-max).
7. **Показывать подтверждённый результат.** `accepted/MAX_ACCEPTED` подтверждает ответ MAX с ID сообщения и совпавшим адресатом, а не прочтение человеком. При `pending/uncertain` результат сверяется без автоматического повтора; для уже созданной попытки ошибка до входа в транспорт записывается `failed`. Ошибка уведомления после бизнес-commit не отменяет сохранённую команду.

При добавлении потребителя проверить разрешённую и запрещённую роли, чужую/выключенную группу, повтор одного ключа без дубля, отказ при изменении допуска и отсутствие отправки при GET/ошибке бизнес-команды. Для событий также проверить, что уведомление возможно только после commit. Использовать [проверки границ чтения](tests/local-max-read-check.php) и [ручного MAX](tests/local-max-manual.php); живой тест требует конкретного разрешённого адресата/сообщения и отдельной сверки результата.

## 6. Что является защитой, а что отдельной задачей улучшения

Сохранять: права, CSRF, versions, точные деньги, idempotency, транзакции, занятость, зафиксированные документы, аудит и сверку внешних результатов.

Отдельно пересматривать по задаче: жёсткие привязки к прежним каталогам/БД/снимкам, одноразовые миграционные допуски, неоднозначные маршруты, дублирующиеся определения, слабую диагностику.

FROZEN в FrozenPacketWire относится к содержимому утверждённого отправляемого пакета. Не путай его с исторической фразой о защите CSS. Если требуется защищённое изменение, найди конкретный механизм и границу, не объявляй всё дерево неизменяемым.

## 7. Горячие точки и постепенное улучшение

- Controller.php, Service.php, ExtraService.php, FinanceController.php, ProviderService.php совмещают много действий.
- Controller::query используется как слой данных из других экранов.
- rental и integrations знают внутренние классы друг друга.
- Один rental_number_guard сериализует основные команды.
- MAX(id)+1 в нескольких местах требует сохранения watermark и плохо подходит для дальнейшего расширения конкурентной записи.
- Runtime/config/миграции недостаточно переносимы.
- SafeErrors сохраняет класс и код ошибки, но почти не даёт контекста для расследования.
- native-source-manifest имеет расхождения с фактическими байтами части файлов; это историческая запись, а не доказательство текущей приёмки.

Желаемое направление для новых и затронутых участков:
- handler разбирает вход и вызывает сервис;
- сервис содержит бизнес-решение и транзакционную границу;
- чтение/запись данных имеют явного владельца;
- renderer использует общую UI-базу;
- адаптер провайдера получает явные параметры и возвращает понятный результат;
- одно бизнес-правило имеет одно авторитетное определение.

Не создавай все эти слои для маленькой надписи. Выделяй ответственность тогда, когда она снижает риск конкретной задачи. Все перечисленные долги не являются предварительным запретом на первую полезную правку.
