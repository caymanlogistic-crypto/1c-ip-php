# Передача задач по аренде в MAX

| Действие | Кому переходит задача |
| --- | --- |
| Направить договор или ДС, повторно направить исправления, передать новую редакцию | Юристу |
| Согласовать договор или ДС у юриста | Бухгалтеру |
| Вернуть от юриста, передать менеджеру замечания бухгалтера | Менеджеру |
| Вернуть от бухгалтера | Юристу |
| Завершить подтверждённую передачу пакета договора или ДС | Менеджеру за подписанным экземпляром, если пакет передал другой сотрудник |
| Открыть вопрос о сдвиге даты либо подтвердить двусторонний акт, после которого впервые возник вопрос по выставленному первому счёту | Бухгалтеру, если вопрос передал другой сотрудник |
| Начать финальную сверку или перевести договор на неё подписанным ДС о завершении | Бухгалтеру и юристу в одном сообщении, кроме роли самого исполнителя |
| Вернуть финальную сверку на доработку | Менеджеру |
| Передать исправленную финальную сверку | Сотруднику из записи возврата |
| Подтвердить юридическое основание по обеспечению | Бухгалтеру |
| Применить ДС с исключёнными помещениями и открытым актом возврата | Менеджеру |

Сообщение содержит номер договора, имя передавшего, исполнителя и задачу. Для ДС добавляется его номер, для переноса обеспечения добавляется связанный договор. При явном назначении указан сотрудник. Если у задачи несколько возможных исполнителей одной роли, указана роль. Реквизиты, контакты и свободные комментарии в шаблон не попадают.

Просмотр, сохранение черновика, передача самому себе, повтор команды и откат не создают новой передачи. Подтверждение состава пакета и подготовка почтовой отправки оставляют задачу у бухгалтера. Самостоятельные статусные уведомления пользуются прежними допусками.

## Допуск

Оба новых режима выключены по умолчанию. Разовый допуск связывает конкретный договор, сотрудника, действие и ключ открытой формы с новой границей событий. Допуск серии закрепляет список пар «ID и номер учебного договора», перечень действий, текущую эпоху, нижнюю границу событий и срок. Оба режима используют один утверждённый профиль, единственную группу `ТЕСТОВАЯ` и закреплённую версию шаблона `staffHandoff`.

Для отдельно согласованной пробы оператор сверяет учебный договор, роль, действие и ключ открытой формы. Утверждение одного нового шаблона и принятие маркера остаются отдельными операциями. Для серии `server-workflow-max-setup.php --enable --staff-handoff-sequence` проверяет согласованный приватный манифест с полями `contracts`, `actions`, `expires_at` и выдаёт маркер для отдельной установки.

Незавершённая попытка `pending` или неизвестный результат `uncertain` серверного workflow блокирует новые отправки через оба маршрута до сверки. Бизнес-переход сохраняется, карточка показывает причину. Старый маршрут не подхватывает уже выбранное событие. После сверки могут отправляться только новые фактические передачи. Подтверждение доставки фоновым SMTP сохраняет переход в истории пакета. Для вызова MAX из фонового процесса нужен отдельный механизм. Подтверждённое выполнение в браузерном журнале операций использует путь после коммита.

## Проверки

- В адресных проверках покрыты смена исполнителя, точное повторное назначение, запрет роли, откат и параллельные команды.
- Подставной транспорт подтвердил две последовательные передачи по одному договору, по одному вызову на событие. Проверены чужие договор и действие, граница событий, эпоха, срок, версия шаблона, профиль и группа.
- Проверки неопределённой доставки подтверждают блокировку по прежним и новым ключам, отсутствие переключения маршрута и повторного проигрывания пропущенных событий. Сценарий с прежним подтверждённым отказом сохранил явный повтор по точечному вопросу.
